# Dashboard Design Notes – Student 1

## Purpose

This document records the design decisions, accessibility choices, and information-architecture rationale for the interactive facility-operations dashboard prototype built as part of Student 1's Phase I contribution.

## Information hierarchy

The dashboard is organised into five distinct layers, each addressing a different decision horizon for a facility manager:

| Layer | Section | Decision horizon |
|---|---|---|
| 1 | Alert banner | Immediate action required now |
| 2 | KPI strip | Current operational status (15-minute window) |
| 3 | Demand chart + Optimisation schedule | Next-hour planning |
| 4 | Federation table + Privacy status | Round-level model health |
| 5 | Model accuracy + AWS health + Tariff window | Analytical and operational monitoring |

## Design decisions

### Colour system

A curated green-and-lime palette maps directly to the project theme (energy, sustainability). Orange is reserved exclusively for warnings and threshold breaches so facility managers can distinguish normal from action-required at a glance without reading any text.

### Data status transparency

A persistent `Live telemetry` badge with a pulsing dot appears in the top bar. A footer note clarifies that Phase I values are simulated and real AWS integration is pending Phase II. The Refresh button allows manual data pulls to reinforce the live-data mental model.

### Privacy-first layout

The differential privacy (ε) budget status is presented as a first-class KPI (top strip) and also as a per-client progress meter in the right column. This surfaces privacy-budget consumption directly to facility managers rather than burying it in a technical log.

### Countdown timer

A live countdown to the next federation round gives facility managers a concrete expectation for when the global model will next update, reducing uncertainty about forecast freshness.

## Accessibility baseline

- Semantic HTML5 elements (`<header>`, `<main>`, `<section>`, `<footer>`, `<nav>`, `<article>`, `<table>`).
- All interactive elements have unique `id` attributes for browser testing.
- ARIA roles: `role="tablist"`, `role="tab"`, `role="meter"`, `role="alert"`, `aria-live="polite"` and `aria-live="assertive"`.
- Screen-reader-only headings (`class="sr-only"`) label chart and KPI sections.
- Colour is never the only distinguishing signal — icons, labels and text always accompany colour cues.
- Keyboard-navigable controls with visible focus states.
- Responsive breakpoints at 640 px, 900 px and 1100 px ensure usability on tablets and mobile devices in facility control rooms.

## Chart design

The bar chart uses CSS custom properties (`--h`) for bar heights so that JavaScript can update them without touching layout. Heights are set as percentages relative to the chart container, making the chart fully responsive without canvas or SVG rendering. A dashed target-ceiling line is drawn with a CSS `border-top` positioned at 18% from the top (equivalent to 900 kW on the 0–1100 kW scale).

## Phase II integration points

| Current behaviour | Phase II replacement |
|---|---|
| Simulated demand values updated by JS | Amazon API Gateway → Lambda → DynamoDB real-time feed |
| Static federation table | WebSocket subscription to IoT Core topic for round updates |
| Alert banner is static | SNS push notification received via API Gateway WebSocket |
| CSV export uses in-browser data | Pre-signed S3 URL generated by Lambda for authenticated download |
| Chart data is random jitter | SageMaker endpoint query for next-interval demand forecast |
